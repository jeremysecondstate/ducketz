# Pareto-scoped recommendations

These are advisory experiments, not implementation instructions or claims of current lift. Each proposal must retain the present authority, point-in-time, readiness, freshness, schema, receipt and lockbox boundaries; failure of any guard keeps or restores the current behavior. No recommendation depends on opening, inspecting or tuning against sealed lockbox outcomes.

## Prediction-accuracy improvements

### 1. Complete the existing gated residual-promotion experiment before changing fast target authority

- Category: Accuracy
- Priority: 1 — High expected value, Medium implementation effort
- Confidence: High that the opportunity exists; Medium that the residual will pass the gate
- Affected loops: Active Pricing; indirectly Directional Loop B; Strategy as a no-regression consumer
- Evidence-backed problem or opportunity: **Confirmed:** the `BLACK-SCHOLES-OP` setup is already implemented, not missing: six semantic inputs feed a Black–Scholes mean plus a 128-component Nyström/Bayesian-ridge normalized residual, calibrated uncertainty, and shape projection. The fast target intentionally keeps its point authority at constrained Black–Scholes while publishing the residual as a receipt-bound sidecar that active Strategy can already consume. The repository also defines baseline-comparison, interval, constraint, lineage, prospective, candidate, lockbox, operational, and separate-authorization gates. `docs/edu/BLACK-SCHOLES-OP.md:441`, `ml/option_pricing/model.py:68`, `ml/option_pricing_runtime.py:1220`, `ml/option_pricing/strategy_shadow.py:298`, `ml/option_pricing/eligibility.py:678`
- Proposed change: Preserve the current staged architecture and use its existing frozen eligibility/candidate protocol as the sole promotion gate. Only if genuinely future, receipt-proven evidence makes every applicable route gate pass, the candidate/lockbox/operational checks pass, and separate authorization is recorded should a canary select the already-computed constrained residual point value for that admitted route. Every absent, stale, unsupported, constraint-failing, unproven, invalid, or unauthorized state must continue to select the exact Black–Scholes baseline. Do not reopen or tune against closed-lockbox targets.
- Mechanism of improvement: The model learns the normalized discrepancy left by Black–Scholes—the same relationship expressed as `f(x)=BS(x)+delta(x)` in the reference—and already supplies posterior uncertainty and coupled surface projection. Conditional route admission can remove repeatable residual bias while the fallback keeps unproven states at the current point estimate. `docs/edu/BLACK-SCHOLES-OP.md:441`, `ml/option_pricing/model.py:729`, `ml/option_pricing/model.py:832`, `ml/option_pricing_runtime.py:1143`
- Expected prediction or efficiency impact: Potentially lower normalized/dollar error for the fast option-pricing point authority on admitted routes and cleaner downstream `opx__` point-residual features. Strategy already consumes the same ready sidecar, so its leg values should remain semantically unchanged by promotion; that equality is a guardrail, not a claimed extra gain. No numeric lift is claimed.
- Risk to the other objective: A gate lookup and model/baseline selection could add latency or computation to the fast path.
- Why that risk is acceptably controlled: Residual inference is already executed before target publication; the proposed canary adds only receipt verification and selection of an existing keyed row using a previously published gate. Black–Scholes remains the unconditional fallback, and no provider call or model fit is added to the target path. `ml/option_pricing_runtime.py:1232`, `ml/option_pricing_loop_native_worker.py:126`
- Validation experiment: Freeze the existing policy/model/candidate identity first; continue collecting both baseline and sidecar on future targets; pair losses within target session and route; evaluate the predeclared gates without changing point authority; only after every promotion boundary passes, canary the selected mean while continuing to record both values.
- Baseline: Current authoritative constrained Black–Scholes point prediction for the exact same contract/target, its separately published sidecar/fallback interval, and target-publication latency.
- Primary metrics: Snapshot-weighted normalized RMSE and normalized absolute/dollar error; error in half-spreads; 80% and 95% interval coverage and width. These fields already exist in Pricing evaluation/model contracts. `ml/parquet_contracts.py:592`, `ml/parquet_contracts.py:597`, `ml/option_pricing/model.py:756`
- Guardrail metrics: Constrained bound/monotonicity/convexity violation rate; median projection correction; source/route coverage; prospective prediction/session count; target publication p50/p95; provider-call count; Black-Scholes fallback rate; exact receipt/clock validity; and equality of Strategy's selected per-leg values/source for the same sidecar evidence. `ml/parquet_contracts.py:469`, `ml/option_pricing/eligibility.py:90`, `ml/option_pricing/eligibility.py:96`, `ml/option_pricing/strategy_shadow.py:298`
- Chronological/out-of-sample evaluation design: Use only predictions frozen before their outcome quote and only outcome evidence later available under the existing causal contract. Require at least the repository’s 60 prospective predictions and 20 sessions per route; use the configured paired-session-blocked 95% method. The assessment/eligibility policy is fixed before this stream; closed-lockbox evidence stays untouched. `ml/option_pricing/eligibility.py:88`, `ml/option_pricing/eligibility.py:120`, `ml/parquet_contracts.py:398`
- Acceptance threshold: Per admitted route, statistically supported strict improvement over Black-Scholes normalized RMSE; interval coverage remains inside the existing 0.72–0.88 and 0.90–0.99 bands; constrained violation rate remains zero; lineage/timing/prospective gates pass; and the upper confidence bound for fast-target latency/provider-call change shows no material regression relative to the frozen baseline. `ml/option_pricing/eligibility.py:92`, `ml/option_pricing/eligibility.py:94`, `ml/option_pricing/eligibility.py:691`
- Rejection/rollback threshold: Any route failing strict loss improvement, coverage, shape, causal lineage, freshness/support, publication-latency, provider-volume, candidate, operational, or authorization guard remains/reverts to Black–Scholes immediately. A missing/corrupt gate must fail to baseline, never to residual authority.
- Repository evidence: `ml/option_pricing_runtime.py:1220`, `ml/option_pricing_runtime.py:1232`, `ml/option_pricing/model.py:729`, `ml/option_pricing/eligibility.py:637`, `ml/option_pricing/eligibility.py:730`, `ml/option_pricing/eligibility.py:764`

### 2. Select probability calibration chronologically instead of fixing Platt everywhere

- Category: Accuracy
- Priority: 2 — Medium-to-high expected value, Low-to-medium implementation effort
- Confidence: High that the mechanism is implementable; Medium that another calibrator wins on any particular horizon
- Affected loops: Directional Loop B; Strategy
- Evidence-backed problem or opportunity: **Confirmed:** the shared calibration module supports identity, Platt and isotonic and fits only caller-provided calibration rows. The production B command fixes Platt; Strategy also hard-codes Platt whenever both classes exist, even though both systems already report later assessment calibration/loss. `ml/calibration.py:10`, `ml/calibration.py:60`, `docs/datafetch-ml/current_start_command:139`, `ml/strategy_selection/model.py:360`
- Proposed change: Within each horizon’s existing chronological calibration partition, use forward-chaining inner folds to compare identity, Platt and isotonic (only when its existing minimum-row/class/support requirements pass). Select by predeclared weighted log loss with Brier/calibration-gap tie-breakers, refit that calibrator on the full calibration window, and preserve the untouched assessment window for admission. If no candidate is strictly better than current Platt, retain Platt.
- Mechanism of improvement: Calibration shape can vary by horizon and evidence density. A one-parameter sigmoid can correct global overconfidence but cannot represent monotone local miscalibration; identity avoids harmful overfitting and isotonic can correct supported nonlinear distortion. Chronological inner selection prevents using later assessment outcomes to choose the mapping. `ml/calibration.py:89`, `ml/calibration.py:118`, `ml/model_runtime.py:677`
- Expected prediction or efficiency impact: Potentially lower horizon/strategy log loss and Brier score and smaller calibration gap, especially where raw-probability distortion is not sigmoid-shaped. No discrimination gain or numeric lift is assumed.
- Risk to the other objective: Fitting up to three one-dimensional calibrators at model-refresh time uses additional CPU; isotonic can overfit sparse support.
- Why that risk is acceptably controlled: Selection occurs only when a model is fitted, not per live row; existing minimum row/class checks remain; compatible model reuse amortizes the work. Reject the change if measured end-to-end refresh or critical-path latency leaves the predeclared baseline confidence band. `ml/calibration.py:86`, `ml/calibration.py:118`, `ml/model_runtime.py:625`, `ml/strategy_selection/model.py:316`
- Validation experiment: Replay consecutive chronological training/calibration/assessment windows for each horizon and loop. On each window, choose using only forward inner-calibration folds, then score the never-used assessment partition. Continue with genuinely prospective LIVE outcomes before promotion.
- Baseline: Current per-horizon Platt behavior, including Strategy identity fallback when calibration has only one class. `ml/strategy_selection/model.py:360`, `docs/datafetch-ml/current_start_command:139`
- Primary metrics: Assessment and matured-LIVE log loss, Brier score and calibration gap per horizon; Strategy profitable-outcome calibration for the top-ranked candidate. `ml/parquet_contracts.py:179`, `ml/runtime_pipeline.py:3631`, `ml/strategy_selection/model.py:733`, `ml/strategy_selection/model.py:819`
- Guardrail metrics: ROC AUC/ranking order, probability support extrapolation, route/evidence counts, Strategy expected-return error and top-candidate realized-return metrics; model-fit and end-to-end cycle time; reuse rate and peak memory. `ml/runtime_pipeline.py:3632`, `ml/strategy_selection/model.py:727`, `ml/strategy_selection/model.py:752`, `ml/strategy_selection/model.py:806`
- Chronological/out-of-sample evaluation design: Preserve current train → calibration → assessment order and boundary purging. Inner folds may split only the calibration interval in forward time. Do not inspect or use closed-lockbox outcomes; prospective confirmation uses predictions frozen before entry and only later-matured exact targets. `ml/model_runtime.py:200`, `ml/strategy_selection/model.py:226`, `ml/strategy_selection/model.py:703`
- Acceptance threshold: Strict improvement in weighted assessment log loss and no worsening of Brier/calibration gap beyond their predeclared sampling confidence bounds for an affected horizon; no loss of discrimination/ranking guardrails; prospective direction agrees; and model-refresh/end-to-end runtime is non-inferior within a baseline measurement-noise bound fixed before the experiment.
- Rejection/rollback threshold: Any assessment or prospective degradation in primary loss/calibration, any causal partition violation, sparse-support failure, material runtime/memory regression, or changed prediction outside the selected calibrator mapping retains/reverts to current Platt/identity.
- Repository evidence: `ml/calibration.py:60`, `ml/model_runtime.py:466`, `ml/model_runtime.py:677`, `ml/strategy_selection/model.py:352`, `ml/strategy_selection/model.py:652`

No additional accuracy recommendation met the required evidence and efficiency-neutrality bar. In particular, this audit does not recommend lowering readiness/freshness/quality gates, expanding target windows around missing data, using post-entry evidence, or changing labels/evaluation definitions.

## Efficiency improvements that preserve prediction accuracy

### 1. Add a receipt-bound cross-cycle materialization cache for Loop B

- Category: Efficiency preserving accuracy
- Priority: 1 — High expected efficiency value, Medium-to-high implementation effort
- Confidence: High that repeated work exists; Medium on realized savings until profiled
- Affected loops: Directional Loop B
- Evidence-backed problem or opportunity: **Confirmed:** every Loop B cycle invokes full rolling materialization, while caches for bars, sources, Parquets, derived data and committed options are allocated inside one invocation and discarded afterward. Model reuse already proves the system accepts exact content/configuration fingerprints as a no-refit boundary. `ml/runtime_pipeline.py:329`, `ml/rolling_materialization.py:176`, `ml/model_runtime.py:625`
- Proposed change: Add an immutable, content-addressed cache for route materialization stages keyed by exact source receipt/checksum inventory, causal input cutoff, symbol/horizon specification, feature-contract/policy versions and cost convention. Reuse only verified prefixes whose keys match; materialize the new suffix; perform the existing schema/natural-key/availability checks on the combined frame. Any absent, ambiguous or corrupt key forces the current full computation.
- Mechanism of improvement: Quarter-hour runs repeatedly read and transform long unchanged histories while only the newest causal suffix usually changes. Reusing exact verified prefixes removes repeated parsing, joins and feature/target calculations without approximating values or changing evidence selection.
- Expected prediction or efficiency impact: Lower critical-path materialization time, bytes read and transient allocations; potentially fewer deadline misses. No prediction change is permitted and no numeric saving is claimed.
- Risk to the other objective: A stale or incompletely keyed cache could reuse data across a changed receipt, availability boundary, feature contract or target definition and therefore change samples/predictions.
- Why that risk is acceptably controlled: The cache is advisory, immutable and checksum/receipt/configuration-bound; cache hits still run current schema, causal clock, natural-key and freshness validation; mismatch/corruption falls back to the existing path. Acceptance requires exact semantic equality, not approximate equivalence.
- Validation experiment: On a chronological sequence of non-lockbox production snapshots, run current full materialization and cached materialization side-by-side from cold and warm states. Inject changed receipts, late rows, corrupt entries, feature-version changes and cutoff changes to prove misses/fail-closed fallback.
- Baseline: Current `materialize_rolling_samples` execution with only its invocation-local caches. `ml/rolling_materialization.py:128`, `ml/rolling_materialization.py:176`
- Primary metrics: Materialization and full Loop B p50/p95 wall time; bytes read; peak memory; repeated Parquet rows decoded; percentage of runs promoted before action deadline.
- Guardrail metrics: Exact equality of route status/source inventory, sample feature/target/clock fields, model compatibility fingerprint, raw/calibrated probabilities, evaluations and publication route counts; log loss/Brier/calibration/reuse metrics must be identical for the same evidence. `ml/runtime_pipeline.py:603`, `ml/runtime_pipeline.py:831`, `ml/parquet_contracts.py:131`, `ml/parquet_contracts.py:156`
- Chronological/out-of-sample evaluation design: Replay evidence in original receipt order and reveal each suffix only at its real availability cutoff. Use train/calibration/assessment and prospective non-lockbox evidence; do not read sealed target values. Compare both paths at every cutoff before measuring performance.
- Acceptance threshold: Zero semantic-field mismatches and identical model/prediction/evaluation fingerprints on every replay/fault case; no new successful route from stale/invalid evidence; and a repeatable strict reduction in at least one primary resource metric with no statistically supported regression in the others or publication timeliness.
- Rejection/rollback threshold: Any output/source/clock/model-fingerprint mismatch, cache hit after a changed dependency, failure to detect corruption, increased deadline misses, or resource regression disables the cache and uses full materialization.
- Repository evidence: `ml/runtime_pipeline.py:329`, `ml/rolling_materialization.py:160`, `ml/rolling_materialization.py:176`, `ml/runtime_pipeline.py:603`, `ml/model_runtime.py:625`

### 2. Persist Strategy’s existing content-addressed historical-outcome cache

- Category: Efficiency preserving accuracy
- Priority: 2 — Medium expected efficiency value, Low-to-medium implementation effort
- Confidence: High
- Affected loops: Strategy
- Evidence-backed problem or opportunity: **Confirmed:** Strategy reconstructs historical candidates/outcomes from exact entry/exit evidence each run. It already computes a SHA-256 key over the policy, Pricing mode, direction probability, sample, entry/exit option surfaces/contracts, stock quotes and applicable Pricing rows, but retains results only in a process-memory LRU. Restarts or evictions therefore repeat deterministic work. `ml/strategy_selection/runtime.py:351`, `ml/strategy_selection/runtime.py:520`, `ml/strategy_selection/runtime.py:607`
- Proposed change: Store each completed outcome-cache value under its existing digest in a versioned immutable local cache with schema/policy/code-contract identifier, output checksum, row count and source-key attestation. On hit, verify the envelope and output; on any mismatch, recompute with the current code and replace only by a new versioned key. Preserve the existing bounded in-memory LRU as the first level.
- Mechanism of improvement: Historical entry/exit candidate construction and outcome evaluation are pure for the exact evidence already included in the key. A verified persistent second-level cache avoids recomputing unchanged decisions across recurring processes while leaving live candidate construction and scoring untouched.
- Expected prediction or efficiency impact: Lower historical-outcome materialization time, repeated option/stock Parquet decoding and CPU after restarts or long histories; model/prediction rows must remain identical. No numeric saving is claimed.
- Risk to the other objective: Serialization drift, an omitted dependency or cache corruption could alter the training outcomes and fitted Strategy probabilities.
- Why that risk is acceptably controlled: The current key already fingerprints every documented immutable input used by one observation. Add explicit schema/code versioning and checksum verification; cache miss/error recomputes; promotion requires byte/semantic equivalence across adversarial dependency changes. `ml/strategy_selection/runtime.py:534`, `ml/strategy_selection/runtime.py:540`, `ml/strategy_selection/runtime.py:557`
- Validation experiment: Run a chronological Strategy replay twice (cold and warm) across process restarts. Compare persisted outcomes, partitions, model manifests, candidate scores/ranks and audits. Mutate each key input in isolated fixtures and corrupt/truncate cache files to require safe misses.
- Baseline: Current in-memory-only LRU, including reported incremental hit/miss counts. `ml/strategy_selection/runtime.py:515`, `ml/strategy_selection/runtime.py:633`
- Primary metrics: Historical-outcome stage p50/p95 time; bytes read; candidate rows reconstructed; persistent and memory cache hit rates; peak memory; total Strategy cycle time.
- Guardrail metrics: Exact equality of outcome rows/status/failures, chronological partition membership, model input inventory/checksum, offline log loss/Brier/calibration/ranking evidence, live raw/calibrated probability, expected return/profit and candidate rank. `ml/strategy_selection/model.py:652`, `ml/strategy_selection/model.py:733`, `ml/strategy_runtime.py:511`
- Chronological/out-of-sample evaluation design: Reveal exact snapshots in original receipt order; compare cold current behavior with warm cache at every Strategy cutoff. Use no lockbox targets; verify that evidence unavailable at a cutoff cannot enter a key or value.
- Acceptance threshold: Exact outcome, model and published candidate/audit equality for every tested cutoff and fault; every changed dependency forces a miss; corrupt/version-mismatched entries fail to recomputation; and repeatable strict reduction in historical-stage time or bytes read with no regression in total cycle time/peak memory beyond the predeclared baseline confidence bound.
- Rejection/rollback threshold: Any cache collision, omitted-dependency hit, causal-clock difference, outcome/model/prediction/rank mismatch, corrupt-entry acceptance, or resource regression disables persistent reads and retains the present in-memory/full-recompute path.
- Repository evidence: `ml/strategy_selection/runtime.py:351`, `ml/strategy_selection/runtime.py:520`, `ml/strategy_selection/runtime.py:570`, `ml/strategy_selection/runtime.py:607`, `ml/strategy_selection/runtime.py:619`

No additional efficiency recommendation met the strict no-accuracy-loss/no-evidence-weakening bar. In particular, this audit does not recommend weakening full receipt/schema validation, reducing provider evidence quality, approximating features, shrinking chronological evidence, or skipping causal/publication checks merely to save time or I/O.
