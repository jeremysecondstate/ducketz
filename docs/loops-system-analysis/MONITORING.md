# Monitoring and recovery

Use [Current system](CURRENT_SYSTEM.md) for the October 11 Atlas responsibility
and native-task observations. Older periodic guardian/LOG instructions are
historical; an absent legacy process is not by itself a failure to restart.

## What each observation proves

| Observation | Establishes | Does not establish |
| --- | --- | --- |
| Source file and installation hash | Inspected/installed bytes at that observation time | Loaded worker version or peer installation |
| Saved task rule and Windows registration | Configured local wake, action and enabled state | Successful numerical responsibility or trader launch |
| Launch result | Worker was requested/started as reported | Completed Stats, Gameplan or combined plan |
| Local preparation receipt | Its exact completed local stages and pinned outputs | Peer package arrival or joint readiness |
| Joint readiness receipt | Verified dated combined outputs and reader selection | Broker execution authority or confirmed fills |
| Stock execution/reconciliation receipts | Their specific order/ownership observations | Success of unrelated horizons, sessions or options orders |

## Preparation and reader checks

Select the intended action date, not whichever latest pointer happens to exist.
Verify original source/configuration bindings, selected scope, required data
readiness, completed stages and output checksums. Current preparation scores
Stats before review/training. Missing history is explicit; missing scores are
not zero. Old attempts retain their original saved order and deadlines.

Check the frozen local Gameplan, Stats and model review separately from a newer
combined UI publication. Confirm the exact owner packages, producer partitions,
one-account plan, combined Stats and dated joint-readiness selection. Do not
credit an earlier session's completion for today's preparation. Directional
counts use each saved universe (24 rows per symbol), not a current fixed count.

The Gameplan and Stats default readers require their own verification. A later
source-binding dependency addendum can explain a dated mismatch without making
an older test a fresh runtime check. Preserve both original and addendum evidence.

## Recovery boundaries

The current responsibility/recovery implementation preserves the run identity,
completed stage receipts, original deadline and any explicit bounded late-recovery
deadline. Inspect the first failed stage and exact owner/lease/source condition.
Reviewed repairs and bounded retries may be supported by that installed procedure;
do not apply the old universal no-retry statement to it.

Never erase a lock, hand-edit a pointer, replace healthy work, retrain completed
stages or replay the old stack to make a status screen green. Configuration,
source installation and ordinary run evidence are separate. A late recovery
must retain actual publication time and pre-action inputs; it cannot silently
rewrite a forecast or expand trading authority.

## Daytime and trader controls

The Trader Representative observes saved status and liveness. Its newer native
prompt includes conditional guarded-start/repair authority, but saved evidence
identifies staged launcher dependencies; older manual-only runbook text differs.
This audit establishes neither automatic-start installation nor a worker launch.
Preserve the human's manual start/stop controls. Atlas's historical stock launcher is
disabled in the October 11 readback. A valid sleeping manual worker requires
matching identity, lock and current heartbeat; an old receipt alone is insufficient.
Before the supported wake, local standby does not imply broker calls or entries.

When active, execution uses actual quotes, usable cash, owned inventory and
confirmed fills. Cumulative catch-up reconciles due net quantities and outstanding
commitments rather than replaying missed instructions. Preserve independent
horizon ownership and rejection guards. A user stop is not permission to restart.
The advisory/paper reader and Loop C observer remain separate from stock execution.

## Historical diagnostics

`ml.system_monitor`, `ml.system_guardian`, old `--forever` processes and their
launch scripts remain diagnostic/reference implementation. Keep their historical
evidence and do not treat old recurrence as current scheduling authority.
Datastore commands can write catalogs even when they do not acquire market data;
this documentation audit inspected saved evidence instead of executing them.
