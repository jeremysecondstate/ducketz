# GitHub-only routine Atlas–Scout coordination

The local profile explicitly selects `coordination_notification_policy`:

- `github_only`: use GitHub for routine coordination; skip Drive API signals.
- `git_and_drive`: retain the older two-channel notification procedure. Missing
  policy fields retain this behavior so an upgrade alone does not change a PC.

Unknown values are rejected. Each PC adopts the reviewed policy locally under
the standing human implementation and installation authority. Preserve the
original profile and installation pointer for an explicit rollback.

## Routes and delivery evidence

| Content | Route |
| --- | --- |
| Sanitized discussion, questions, ownership, handoffs and verification | Existing atlas-scout GitHub files, Issues and Project |
| Shared source, reviewed outputs, immutable machine notices and correlated requests | Existing Ducketz Git transport and completion queues |
| Private Gameplan/Stats exports, account snapshot, combined plan and adoption packets | Existing privately bound CODEXSTORE nightly exchange |

Keep the Ducketz profile's repository, remote, machine identity, source branch
prefix, locks, request queues, incoming-source refs, completion IDs and receipts.
Do not repoint its remote to atlas-scout. Never move private packets into Git or
remove the CODEXSTORE mount as part of this notification cutover.

With `github_only`, skip Drive connector metadata reads, fetches and writes,
including cached-signal revalidation. All `drive-*` CLI actions return
`DISABLED_BY_POLICY` before opening a Drive binding, evidence file or state.
That result means the transport is retired by local policy, not that anything
was delivered. It is not a failure to repeat in every scheduled final.

Git notice delivery remains based on verified Git publication and remote SHA
readback. Request replies retain their original IDs, hashes and Git receipt
correlation. A reported notice does not complete pending source review or a
request. Retiring Drive does not mark any of those records finished.

## Bounded scheduled wake

1. Verify the installed release and read this PC's profile and current memory.
   If the selected policy is `github_only`, do not access Drive signal bindings
   or report missing Drive evidence as a blocker.
2. Inspect relevant new atlas-scout Git/Issue changes under the existing lock
   and saved cursor. Use existing authentication, normal fetches without
   recursion, owned-path commits and exact remote readback. Preserve concurrent
   edits. Route work to its existing owner and exchange substantive results
   directly; no human relay or duplicate acknowledgment loops.
3. Continue the existing bounded Ducketz `observe`, `inbox-scan`, `inbox-read`,
   `inbox-mark`, notice `deliver`, `request-*` and `incoming-*` procedures when
   applicable. Keep their separate durable cursors and limits. These use Git
   independently of Drive; no new scanner, schedule or model wake is needed.
4. Review and implement applicable handoffs under standing authority. Record
   source publication, local installation, task configuration and runtime state
   separately. Run only relevant supported checks; preserve healthy workers.
5. Persist one meaningful outcome or the bounded unchanged cursor. Finish the
   model turn normally. Scheduled model runs never archive themselves or other
   chats; the separately installed Windows cleanup task handles eligible chats.

## Adopt on each PC

1. Capture the current profile, native definitions, memory, active release and
   relevant queue/receipt identities. Inspect any genuinely interrupted Drive
   write and preserve its exact disposition; a historical field named `pending`
   with `stage: published` is not an unfinished write. Source records marked
   `delivery_stage: not_prepared` are not automatically undelivered notices.
2. Review the exact source commit and run the offline coordination CLI, task,
   notice/request, source-intake and installation checks. Install the immutable
   coordination subset with the supported installer; retain prior releases.
3. Add only `coordination_notification_policy: github_only` to the local profile.
   Preserve all existing fields, bindings and private packet configuration.
4. Update native prompts through the native automation interface, preserving
   identities, schedules, model settings, notification preferences and context.
   Use the new installed release. Replace active Drive instructions with this
   procedure; preserve historical memory bytes and mark obsolete warnings as
   historical so they are not replayed as current failures.
5. Verify the manifest, exact profile/native readback, disabled Drive guard and
   normal Git inbox/request status. An ordinary scheduled wake supplies runtime
   evidence; do not launch a new model run just to demonstrate the cutover.
6. Publish one substantive adoption receipt through atlas-scout, with exact
   source, local checks, installed policy and any actual remaining dependency.
   Verify each PC separately; a peer's adoption is not local-installation proof.

The earlier claim that a Scout `pc-new` peer binding conflicts with an Atlas
`pc-original` profile is not, by itself, an error: a peer signal is expected to
identify the other machine and address this recipient. Preserve old evidence
without renaming either machine. GitHub-only operation does not need that
retired signal check.
